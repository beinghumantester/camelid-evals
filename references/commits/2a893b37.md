# Commit `2a893b37` — stop-sequence streaming duplication

**Full hash:** `2a893b374985e63f5fdfaaa35a060b8959029317`
**Date:** 2026-09-06 (postdates both `v0.6.1` and `v0.7.0` — as of this
writing this fix exists only on `main`/HEAD, in no tagged release; see
`docs/V0.6.1_DRIFT_AUDIT.md`).
**Title:** `fix(api): stop the dense streaming lane duplicating a reply on a straddling stop`

**Used by:** `evals/regression-museum/cases.json` (cases 1 and 2, the
KB-1/KB-2 split), `skills/camelid-regression-museum/SKILL.md`,
`mock-server/server.ts`'s `BUG_MODE=stop_straddle` toggle.

## The bug

A stop string that straddles a token boundary made the dense streaming
lane re-emit the whole reply as one extra delta, on top of everything
already streamed — the client sees the prefix twice.

Root cause, in the commit's own words:

> `streamed_text` after step n-1 is the UNTRUNCATED decode, which by
> construction contains no stop match. A match found at step n must
> therefore END past `len(text_{n-1})` but may START before it.
> `truncate_at_stop_sequence` cuts at the match START, so the truncated
> text is strictly SHORTER than what the client already holds,
> `strip_prefix` returns `None`, and the
> `unwrap_or_else(|| text.clone())` fallback sends the entire reply again.

## The exact repro (used verbatim in this project's cases)

Stop sequence `"><"`, `max_tokens: 2`, where the generated tokens decode
to `"<unk>"` each:

```
delta 1: "<unk>"      <- full, untruncated
delta 2: "<unk"       <- the entire truncated reply, re-emitted
client:  "<unk><unk"  vs non-streaming "<unk"
```

This project's `expectedStreamedTextBeforeFix` (`"<unk><unk"`) and
`expectedNonStreamText`/`expectedStreamedTextAfterFix` (`"<unk"`) in
`evals/regression-museum/cases.json` are these exact bytes, not derived
values.

## Why the bug is streaming-only

The non-streaming lane was never affected — it already returns the
correctly-truncated `"<unk"` both before and after this fix. That's why
`RegressionMuseumCase` has a single `expectedNonStreamText` field but two
streamed-text fields (`Before`/`AfterFix`): drift in the non-streaming
lane would be a *different*, new defect, not this one.

## The fix (for context; not itself re-verified beyond the commit message)

Reuses `stop_safe_stream_len` from the runnable lane so bytes a later cut
would remove are never streamed in the first place, releasing the settled,
truncated text on the terminating step instead. Three supporting pieces
per the commit message: `stream_delta`'s fallback change (empty instead of
resending the whole reply), `stop_hold_back_flush` (releases a held tail
at every terminal exit, not just the normal one), and seeding
`streamed_text` from a prompt-cache hit with the same bound.

The commit's own regression test,
`streaming_completion_stop_straddling_a_token_matches_the_nonstreaming_answer`,
reassembles the SSE stream exactly as a client does and pins it to the
non-streamed answer — "Verified to FAIL on the parent commit and pass
here." This project's KB-2 case is the same idea, run from outside the
Rust codebase against the live HTTP surface.
