# v0.6.1 drift audit

This project is pinned to the exact Camelid version installed on the test
laptop: **v0.6.1** (official `camelid-linux-x86_64.tar.gz` release,
checksum-verified). Every eval oracle in this repo either cites v0.6.1
source directly, or — where a later HEAD state was cited by mistake during
early drafts — was re-audited against v0.6.1 specifically. This document
records that audit so a future contributor doesn't have to redo it, and so
future version bumps have a clear "what changed" trail to extend.

## Method

For every claim, the same three git commands decide it:

```
git show v0.6.1:<path>                        # what a file looked like AT that tag
git diff v0.6.1 HEAD -- <path>                 # everything that changed since
git merge-base --is-ancestor <tag-or-commit> <other>   # strict ordering between two refs
```

A claim is only written down here as "confirmed at v0.6.1" if one of these
commands was actually run against the real cloned repository — never
inferred from HEAD behavior or from documentation prose alone.

## Findings

### 1. `src/api/contract.rs`'s `API_CONFORMANCE_CASES` grew after v0.6.1

**20** self-declared conformance cases exist at the `v0.6.1` tag; **28**
exist on the `main` HEAD used during this project's research (560 commits
ahead of `v0.6.1`). The `sampling_temperature`, `sampling_top_p`,
`sampling_top_k`, `sampling_min_p`, `sampling_seed`, `sampling_stop`, and
`sampling_repeat_penalty` entries, specifically, are HEAD-only additions
— they do not exist as named registry entries at v0.6.1.

**This does not mean the underlying behavior is new.** The runtime
validation and the typed `invalid_sampling_parameter` error code were
independently confirmed present in `src/api/mod.rs` at v0.6.1 (hits at
lines 10266, 10275, 15656, 15665) and asserted in
`tests/api_vertical_slice.rs` (lines 2021, 2044, 2067, 2090) at that same
tag. So: the *behavior* is real for v0.6.1, but citing it as "contract.rs's
`sampling_temperature` case" would be citing a registry entry that didn't
exist yet. `evals/self-conformance/cases.json`'s `evidence` block on each
affected case (SC-1 through SC-6) makes this split explicit via
`registryEntryPresentAtVersion: false` alongside a v0.6.1-real
`evidenceReference`.

Two sub-claims were **not** fully isolated and are marked `UNVERIFIED`
rather than asserted:

- SC-7/SC-8 (empty `stop` array / more than 4 stop sequences): only the
  general `invalid_sampling_parameter` machinery was confirmed at v0.6.1,
  not the exact `stop`-array-bounds validation line.
- The exact per-parameter line mapping inside `tests/api_vertical_slice.rs`
  (which of the 4 assertions maps to which parameter) was not isolated for
  `top_p`/`min_p`.

### 2. The `2a893b37` streaming-duplication fix is NOT in v0.6.1 — or v0.7.0

```
$ git merge-base --is-ancestor v0.6.1 2a893b37 && echo "fix postdates v0.6.1"
fix postdates v0.6.1
$ git merge-base --is-ancestor v0.7.0 2a893b37 && echo "fix postdates v0.7.0"
fix postdates v0.7.0
```

The fix commit is dated 2026-09-06, after the `v0.7.0` tag itself
(2026-09-06, ~3.5 hours earlier). As of this writing it exists only on
`main`/HEAD, in no tagged release at all. This is the single most
load-bearing finding in this audit: an earlier draft of
`evals/regression-museum/cases.json` asserted the POST-FIX text as the
correct expectation, which would have made every real run of this project
report a false `FAIL` against the actual pinned laptop. See
`references/commits/2a893b37.md` and the KB-1/KB-2 split in
`skills/camelid-regression-museum/SKILL.md` for how this was corrected.

### 3. `a6b660cf` (agent tool-calling fix) IS in v0.6.1

```
$ git merge-base --is-ancestor a6b660cf v0.6.1 && echo "included in v0.6.1"
included in v0.6.1
```

Landed 2026-06-28, well before the `v0.6.1` tag (2026-08-08). Not built
into a regression-museum case regardless — see

loop, not just the chat-completion HTTP surface).

### 4. `config/runtime-capabilities.json` — confirmed present at v0.6.1, all 7 projects

`git show v0.6.1:config/runtime-capabilities.json` returns the file
verbatim with all 7 projects (`runtime-capability-registry`,
`mixtral-moe-completion`, `cpu-kquant-prefill-owner`,
`indexed-ngram-speculation`, `unified-kv-sequence-pool`,
`continuous-batch-scheduler`, `production-server-hardening`) — transcribed
into `fixtures/runtime-capabilities.json` with no HEAD-only additions
found in this file specifically (unlike `contract.rs`).

### 5. `ledger/camelid-ledger.json` model rows — confirmed present at v0.6.1

All five ledger rows this project's `fixtures/model-profiles.json`
references (`tinyllama_1_1b_chat_q8_0`, `llama32_3b_instruct_q8_0`,
`nomic_embed_text_v1_5_q8_0`, `qwen3_0_6b_instruct_q8_0`,
`gemma_3_1b_it_q8_0`) were confirmed present at v0.6.1 with the
`tool_capable`/capability fields this project depends on.

## When to re-run this audit

Any time the pinned laptop's Camelid version changes (a new
`camelid-linux-x86_64.tar.gz` release is installed), every citation above
tagged "confirmed at v0.6.1" needs the same three-command treatment
against the new tag before this project's oracles can be trusted again —
per the evaluator's own governing principle: never upgrade an untested
capability to a passing status just because the version number moved.
